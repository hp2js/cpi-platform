## Conflicts between the brief and this repo (need a decision)

| Brief says                                                       | Repo reality                                                                                                                                           | Recommendation                                                                                                                                                                 |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

Switching libraries would duplicate the contract (rule 0.4).                                                    |
| `@nestjs/config` + `registerAs`                                  | `config.ts` already validates env with zod and fails fast; exposed as the `CONFIG` token                                                               | **Keep.** Adding `@nestjs/config` brings in a dependency without new behaviour.                                                                                                |

| Repository per feature                                           | ~360 DB lines across controllers                                                                                                                       | See decision below.                                                                                                                                                            |

## Refactor order

Each step builds, lints and passes all 129 integration tests, then gets its own commit.

0. **Cross-cutting:** `DatabaseModule` (`@Global`, provides `DB` from `Infrastructure`), message/code option on `SchemaValidationPipe`, `@OverrideReason()` param decorator (for V6), move `loadConfig(process.env)` into `config.ts`.
1. **health, dev, admin, events** — least coupled.
2. **directory, supervision** — read-heavy; `scope.ts` is shared and is extracted into a service here.
3. **reporting, review** — workflow core; depend on directory/scope.
4. **planning** (3 controllers), **annual**.
5. **cycle** (forms + settings, the largest at 1372 lines).
6. **auth** (session + account) and **simulation** last, done deliberately: cookies, session store, reset boundary.

Per module: `<feature>.module.ts` + `<feature>.service.ts` (handler bodies move verbatim, keeping `write(...)` and its lock), `safeParse` moves into pipes with the same messages, the controller ends up thin, plus a service unit test with a mocked data layer.

## Open questions

1. **Repositories or not?** Strict 2.2 means a repository layer under every service (~360 query sites). Alternative: services own their Drizzle queries through the injected `DB`, and repositories are extracted only for shared queries (users-by-email, scope, cycle). The second option gets the same thin controllers with roughly half the churn. **Recommend the second.**
2. **Service unit tests** with mocked repositories (2.13) duplicate the 129 integration tests. Add them only for pure branching logic?
3. Confirm the zod-over-class-validator and keep-`config.ts` decisions above.

## Decisions (confirmed 2026-10-04)

- **Repository per feature** (strict 2.2): every Drizzle query moves into `<feature>.repository.ts`. Services orchestrate and own the `write(...)` transaction boundary, and pass `tx` to repository methods.
- **Keep zod + `config.ts`**: `SchemaValidationPipe(contractSchema)` in place of class-validator DTOs; no `@nestjs/config`.
- **Unit tests only for pure service logic**; the HTTP integration suite remains the characterisation suite.
