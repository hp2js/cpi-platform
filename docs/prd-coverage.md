# PRD coverage: frontend and mock API

Scope: `apps/web` against the mock API · Source: PRD v1.1 (`docs/HP2JS — Adili-V3-Track-2-PRD.md`) · Checked: 27 September 2026

How each functional requirement and mandatory scenario is met in the frontend and the mock API that stands in for the backend, and what verifies it. Tests: `apps/web/src/mocks/*.test.ts` (API rules) and `e2e/*.spec.ts` (browser journeys). "Mock" means the rule is enforced by the mock and must be re-implemented by the real API (see `docs/api-handover.md`).

## Configuration the administrator controls

| Setting                                                                                           | Where                              | Rule                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Scoring profiles (weights, procedures scored or prerequisite, foundation checklists, source note) | Forms & scoring → Scoring profiles | Copy, edit a draft, approve, apply to the cycle. A profile is cycle-wide, not per form version, and locks when the first form version is published (§7.1). A different profile is tried in a new simulation run. The 23rd Cycle structure is a reference that must be copied and approved before use. |
| Reporting calendar and reminders                                                                  | Setup → Reporting calendar         | Future dates only; reason required; institutions and officers notified.                                                                                                                                                                                                                               |
| Users and institutions                                                                            | Setup → Users & institutions       | Fictional addresses; deactivation keeps history.                                                                                                                                                                                                                                                      |
| Officer portfolios                                                                                | Setup → Assignments                | Reason required; history kept.                                                                                                                                                                                                                                                                        |
| Form versions                                                                                     | Forms & scoring → Reporting forms  | Unopened periods only; scored criteria locked after activation.                                                                                                                                                                                                                                       |
| Evaluation extensions                                                                             | Publication → Annual evaluation    | Per institution, authorized, never shortening a window.                                                                                                                                                                                                                                               |

## Not built, and why

| Item                                                                                                                                           | PRD                                                            | Status                                                                                                                                                                                                 |
| ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Administrator support access to drafts and institutional responses                                                                             | §5.2 ("elevated support action", "logged support access only") | Not built. Needs a decision on when support access is allowed.                                                                                                                                         |
| Procedures as an enforced prerequisite                                                                                                         | §10.1                                                          | A prerequisite profile shows procedures as met or not met with no points; nothing is blocked by it. The PRD keeps this structure as a reference, not an operational profile.                           |
| Configurable checklist items as a question type                                                                                                | FR03                                                           | Foundation checks are configured per profile; form questions have no checklist type.                                                                                                                   |
| Full-text search, extra channels, AI evidence assistant                                                                                        | §6.2, §14                                                      | P1 or optional.                                                                                                                                                                                        |
| Performance and scale rehearsal                                                                                                                | §4.2                                                           | Backend measurement.                                                                                                                                                                                   |
| Production authentication (Argon2id hashes, HTTP-only cookies, server-side throttling), eCitizen sign-in, storage, malware scanning, retention | §13                                                            | The mock shows the behaviour (invitations, resets, lockout, generic errors); the backend must provide it securely. eCitizen needs an agreement and OpenID Connect credentials (see `api-handover.md`). |
| A summary of what a clock advance did                                                                                                          | FR14 (usability)                                               | The email sink and audit log show it; there is no summary on the Simulation page.                                                                                                                      |
| Plan milestones for onboarded institutions                                                                                                     | FR04, §4.2 scale                                               | New institutions start with the mandatory CPC and IAO milestones only; there is no import of their approved plan milestones yet.                                                                       |
| Onboarded institutions across simulation runs                                                                                                  | FR14                                                           | “Start a new run” restores the seeded fixture set (eight institutions); onboarding is repeated per run. Scoring profiles carry over; the calendar returns to its seeded defaults.                      |
