# Code quality and risk review

Scope: the whole repository at `af4e560` on `main` (2026-10-08): `../apps/api`, `apps/web`, `packages/contracts`, `e2e`, `infra`, `.github/workflows`, `docker`, `scripts`, `security`. This is a read-only review: no code was changed.

## How this was done

1. **Automated, Sonar-style metrics.** ESLint ran over all production TypeScript with rules the repo does not configure: `complexity` 15, `max-depth` 4, `max-params` 4, `max-lines-per-function` 80, `max-lines` 500, `no-nested-ternary`, `no-non-null-assertion` and `no-magic-numbers`. Tests, fixtures and shadcn `components/ui` were excluded. A 10-line normalised clone detector measured duplication. Greps covered other artefacts (TODO, `eslint-disable`, `as` casts, `console`, clock use).
2. **Manual review** in five slices: API platform/security core, API feature modules, web routes/shell, web features + MSW mock, and contracts/infra/CI/e2e. Each finding was checked against the code. The highest-risk ones were re-verified independently; the ReDoS was reproduced and timed.

## Risk model

Each finding gets **Impact** (1–3) and **Likelihood** (1–3). **Risk = Impact × Likelihood.**

| Tier         | Rule                                                                                                 | Meaning                                       |
| ------------ | ---------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| **Critical** | Risk 6–9 **and** the category is security, data loss/integrity, or availability of the whole service | Fix before the next production release        |
| **High**     | Any other finding with risk 6–9                                                                      | Schedule in the next sprint                   |
| **Medium**   | Risk 3–4                                                                                             | Plan into regular work                        |
| **Low**      | Risk 1–2, or maintainability with no direct user effect                                              | Opportunistic / boy-scout fixes, lint ratchet |

- **Impact:** 3 = account takeover, data loss, a wrong official result or a full outage. 2 = one user or flow broken, or a rule (PRD/CLAUDE.md) violated. 1 = cosmetic or developer friction.
- **Likelihood:** 3 = happens in normal use. 2 = needs concurrency, a slow network or an unusual but legitimate input. 1 = needs a misconfiguration, an attacker with prior access, or a rare race.
- **Deployment context:** prod sets `DEMO_MODE=false` explicitly (`infra/platform/envs/prod.tfvars:5`). Real uploads are off unless `REAL_DOCUMENT_UPLOADS=true`. Staging is a demo with uploads on.

## Summary

The codebase is disciplined. Strict TypeScript, schema-validated I/O on both sides and envelope errors that never echo input are all in place. Scope checks return 404, cookies are hashed and timing-safe, actions are SHA-pinned, images are signed, and the data tier is private. Most of the risk sits in five areas:

1. **Auth state races.** Sign-in code and password-lockout checks are read-then-increment, so parallel requests defeat them. Sessions also survive a password reset.
2. **The single global write lock** is held across slow I/O: S3 PUT, scrypt, email, and a **quadratic regex over uploads**. One request can stall every writer and exhaust the pool.
3. **Workflow-rule edges** that produce wrong official results. A quarter can be finalized without an approved baseline (it then shows as 0 in oversight). Lateness changes retroactively. Publish double-writes on duplicate IDs. A reschedule ignores the target lock.
4. **Business rules implemented twice** (API and MSW mock) instead of in `@cpi/contracts/domain`. The duplicated bugs show the copies already drift together.
5. **Frontend data-flow bugs** that lose user edits. The frontend also computes rules that CLAUDE.md says only the API may compute.

## Critical

### C1. ReDoS: quadratic regex in PDF inspection freezes the API

- **Category:** Vulnerability. **I3 × L2 = 6**
- **Where:** [uploads.ts:128-129](packages/contracts/src/domain/uploads.ts:128). It runs inside `write()` from [reporting.service.ts:156](apps/api/src/reporting/reporting.service.ts:156) and [foundations.service.ts:94](apps/api/src/planning/foundations.service.ts:94).
- **Evidence:** `.replace(/stream\r?\n[\s\S]*?endstream/g, '')` runs over the whole file (up to 20 MiB). Reproduced: a file of repeated `stream\n` with no `endstream` and a trailing `%%EOF` takes 0.37 s at 100 KB, 1.5 s at 200 KB and **5.2 s at 400 KB**. 20 MiB would take hours. Node is single-threaded, and the check also runs while the global write lock is held.
- **Fix:** replace the regex with a linear `indexOf('stream')` / `indexOf('endstream', from)` scan that stops when `endstream` is missing. Add a unit test with a 1 MB crafted input and a time budget. Move `checkUpload` out of the write lock (see C2).

### C2. Global write lock held across slow I/O; pool of 10 → whole-API outage

- **Category:** Availability. **I3 × L2 = 6**
- **Where:** [db.ts:31-47](apps/api/src/database/db.ts:31), [infrastructure.ts:34-41](apps/api/src/infrastructure.ts:34) (`max: 10`, `connectionTimeoutMillis: 1500`), [files.ts:46-61](apps/api/src/storage/files.ts:46) inside [reporting.service.ts:130-209](apps/api/src/reporting/reporting.service.ts:130), [session.service.ts:253-267](apps/api/src/auth/session.service.ts:253), bulk invites at [people.service.ts:486,528](apps/api/src/cycle/people.service.ts:486), and the storage GC at [maintenance.ts:66-83](apps/api/src/storage/maintenance.ts:66)
- **Evidence:** these all run under `pg_advisory_xact_lock`: the S3/Azure PUT (15 s timeout) plus its verify GET, file inspection, ~128 MiB scrypt per invited user, and the email-sink insert. Every waiter also holds a pool connection, so `AuthGuard` lookups time out and reads fail too.
- **Fix:**
  - Do slow work before `write()`: hash, inspect and PUT the object first (`withUpload` already compensates for orphans). Keep the transaction to the metadata insert.
  - Set `lock_timeout`, or use `pg_try_advisory_xact_lock` and return 503.
  - Give writers their own small pool.

### C3. Sign-in code (second factor) brute-forceable through parallel requests

- **Category:** Vulnerability. **I3 × L2 = 6**
- **Where:** [sessions.ts:172-191](apps/api/src/auth/sessions.ts:172)
- **Evidence:** the flow is `hgetall` → compare → `hincrby(attempts)` → `del`. N concurrent guesses all read the challenge before any of them increments the counter, so the 5-attempt limit doesn't hold against a 10⁶ code space. `HINCRBY` on a key that just expired also recreates it with no TTL.
- **Fix:** reserve the attempt atomically before comparing: a Lua script (or `MULTI`) that does `HINCRBY`, then `PTTL`, and rejects when attempts exceed the limit or the key is gone. Add a `Promise.all` burst test.

### C4. Password lockout bypassable by bursts; no rate limiting; scrypt makes sign-in a DoS lever

- **Category:** Vulnerability. **I2 × L3 = 6**
- **Where:** [session.service.ts:125-143](apps/api/src/auth/session.service.ts:125), [sessions.ts:106-124](apps/api/src/auth/sessions.ts:106), [passwords.ts:43,89-91](apps/api/src/auth/passwords.ts:43)
- **Evidence:** `lockedFor` is read before `passwordMatches`, and `recordFailure` runs after it, so parallel attempts all pass the check. Each attempt, including the dummy hash for unknown emails, costs ~128 MiB of scrypt. There is no throttler and no `trust proxy`. Anyone can also lock any email for 15 minutes ([sessions.ts:114-124](apps/api/src/auth/sessions.ts:114)).
- **Fix:**
  - `INCR` the failure counter before verifying.
  - Add `@nestjs/throttler` per IP and globally, and `app.set('trust proxy', 1)`.
  - Cap concurrent scrypt calls with a semaphore.
  - Key lockout on (email, IP), with a looser per-email limit.
  - Consider Front Door WAF rate rules (see H8).

### C5. Password reset and change do not revoke existing sessions

- **Category:** Vulnerability. **I3 × L2 = 6**
- **Where:** [session.service.ts:252-287](apps/api/src/auth/session.service.ts:252), [account.service.ts:54-90](apps/api/src/auth/account.service.ts:54). `endAllFor` is only called on role change ([people.service.ts:259](apps/api/src/cycle/people.service.ts:259)).
- **Evidence:** a stolen session keeps working after the victim resets their password. Related problems:
  - Sessions slide forever server-side, while the cookie has a fixed 8 h `maxAge` ([sessions.ts:74-80,198-200](apps/api/src/auth/sessions.ts:74)).
  - The `user-sessions:*` set is never pruned, and `set`/`sadd` are not atomic, so some sessions become unrevocable.
  - Session IDs are stored raw as Redis keys.
- **Fix:**
  - Call `sessions.endAllFor(user.id)` after commit in both flows, and re-issue the caller's own session.
  - Store `createdAt` and enforce an absolute lifetime.
  - Use `MULTI` for `set` + `sadd` + `expire`, and `srem` in `end()`.
  - Key sessions by `sha256(id)`.

### C6. Report edits silently lost (save race, upload stale closure, stale cache on revisit)

- **Category:** Data loss. **I3 × L2 = 6**
- **Where:**
  - [use-report-form.ts:12-15](apps/web/src/features/reporting/use-report-form.ts:12) and [institution/report.tsx:170-178](apps/web/src/routes/institution/report.tsx:170)
  - [report-fields.tsx:402-414,683-684,739-744](apps/web/src/features/reporting/report-fields.tsx:402)
  - `disabled` never passed to fields: [report-fields.tsx:151](apps/web/src/features/reporting/report-fields.tsx:151), [report.tsx:420-439](apps/web/src/routes/institution/report.tsx:420)
- **Evidence:**
  1. Save sends a snapshot, then `markSaved` calls `form.reset(server answers)`, which reverts anything typed while the request was in flight. Fields aren't disabled during the save, and several controls ignore `disabled` entirely.
  2. `onUploaded` closes over the `answer` from the render where the upload started, so toggles or other uploads made during a slow upload are overwritten.
  3. Save never updates `['reports', id]`. Returning within gcTime remounts the editor from stale answers and a stale `version`, so the next save gets **409 on the user's own work**.
- **Fix:**
  1. In `markSaved`, reset only if the current values still equal the submitted snapshot; otherwise move the defaults and keep the form dirty.
  2. Use a functional update that reads `form.getFieldValue(path)` when the upload completes.
  3. `setQueryData(reportKeys.bundle(id), …)` with the returned draft.
  4. Thread `disabled` through every control.
  5. Add RTL tests for type-during-save and upload-during-edit.

### C7. Cloud identities over-privileged (OIDC subjects, web identity, DB admin login)

- **Category:** Vulnerability (least privilege). **I3 × L2 = 6**
- **Where:**
  - Drift identity: [bootstrap/main.tf:173-176](infra/bootstrap/main.tf:173). Subject `ref:refs/heads/main` holds `Key Vault Contributor` + `Secrets User` on all environments, and every main-branch job with `id-token: write` can mint it ([deploy.yml:83-88](.github/workflows/deploy.yml:83), [security.yml:166-168](.github/workflows/security.yml:166)).
  - PR plan identity: reads `tfstate-staging`, which contains the Redis access key ([bootstrap/main.tf:167-170,246-251](infra/bootstrap/main.tf:167)).
  - Web container: carries the identity with KV-secrets and Blob-contributor roles ([apps.tf:59-62](infra/platform/apps.tf:59)).
  - Database: the API connects as the PostgreSQL server admin ([main.tf:278,314](infra/platform/main.tf:278), [apps.tf:30](infra/platform/apps.tf:30)).
  - Deployer: RBAC Administrator has no ABAC condition ([bootstrap/main.tf:206-216](infra/bootstrap/main.tf:206)).
- **Fix:**
  - Federate drift on a dedicated `environment:drift` subject, and drop `id-token` from jobs that don't need it.
  - Use Entra auth for Redis so no key sits in state.
  - Remove the `identity` block from the web app.
  - Create a DML-only runtime DB role and keep the admin role for the migration job.
  - Add an ABAC `condition` that limits which roles the deployer can assign.

### C8. Wrong official results: finalize without an approved baseline, and pending scores shown as 0

- **Category:** Data integrity. **I3 × L2 = 6**
- **Where:**
  - [review/data.ts:159-176](apps/api/src/review/data.ts:159)
  - [review.service.ts:809-842](apps/api/src/review/review.service.ts:809)
  - [annual/data.ts:645-648,741-746](apps/api/src/annual/data.ts:645), the same pattern in the mock at [mocks/handlers/oversight.ts:131](apps/web/src/mocks/handlers/oversight.ts:131)
- **Evidence:**
  - `baselineOf` ignores `status`, and `finalize` only checks for undecided milestones. With zero milestones, or a proposed/returned baseline, the quarter finalizes but is evaluated as pending forever.
  - Oversight turns pending into `{numerator: 0, denominator: 1}`. That violates the rule "pending is never shown as zero" and drags averages down.
- **Fix:**
  - Add `approvedBaselineOf` in contracts/domain, and return 422 `baseline_not_approved` from `decide` and `finalize`.
  - In oversight, exclude pending rows from averages and comparisons, and count them separately.
  - Add tests in the API and the mock.

### C9. Lateness rewritten retroactively when day-counting settings change (FR02)

- **Category:** Data integrity. **I3 × L2 = 6**
- **Where:** [settings.service.ts:305-339,410-421](apps/api/src/cycle/settings.service.ts:305), [annual/data.ts:137-144,783-785](apps/api/src/annual/data.ts:137), [digests.ts:101](apps/api/src/simulation/digests.ts:101)
- **Evidence:** `quarterDisposition` recomputes `daysLate(firstSubmittedAt, deadline, cycle.dayCounting)` from the _current_ settings. The receipt stores the value at issue time, so published evaluations and receipts can disagree.
- **Fix:** evaluate from the receipt's stored `daysLate`/`daysLateUnit`, or snapshot `dayCounting` per period when reporting opens. Add a test that changes the mode after a submission.

### C10. Reschedule amendment confirmed into a locked target quarter (AT17)

- **Category:** Data integrity. **I3 × L2 = 6**
- **Where:** [planning.service.ts:439-444,474-484](apps/api/src/planning/planning.service.ts:439), the same pattern in the mock at [mocks/handlers/planning.ts:553-559](apps/web/src/mocks/handlers/planning.ts:553)
- **Evidence:** only `source` is lock-checked. The target is loaded with `latestBaseline(...)!` and gets a new version, which retroactively changes a locked denominator.
- **Fix:** check `this.locked(tx, target)` and that the target exists, and return 409 `baseline_locked` otherwise. Add an integration test.
