# API handover: contracts the frontend depends on

Status: draft for HP2-9 · Owner of the real API: backend (Patrick) · Frontend reference implementation: `apps/web/src/mocks/`

The frontend is complete against a mock API. This document lists every endpoint it calls, who may call it, and the rules the mock enforces. Those rules are what the screens rely on, so treat them as acceptance criteria for the real API. Where the PRD leaves a choice open, the mock takes the PRD's proposed default; change it here and in the schemas together.

## How to use this

- **Schemas** live in `packages/contracts/src/draft/` (zod, exported from `@cpi/contracts`). The frontend validates every response against them, so a shape mismatch shows as "The server returned an invalid response". Adopt them in Nest with the existing `SchemaValidationPipe`, or revise them and update the frontend in the same change.
- **Errors** use the existing envelope `{ message, fieldErrors?, requestId?, code? }`. The frontend branches on `status` and `code` (listed below), shows `message` to users, and maps `fieldErrors` keys to fields. Messages must never contain submitted content.
- **Retiring the mock:** implement an endpoint, delete its handler from `apps/web/src/mocks/handlers/`, run `pnpm check` and `pnpm test:e2e`. Requests with no mock handler already pass through to the real API, so endpoints can move one at a time. The mock's tests in `apps/web/src/mocks/*.test.ts` describe the expected behaviour and can be ported to API integration tests.
- **Times** are ISO-8601 instants with an offset. Business time comes from the server's clock (simulated in the demo); the browser never decides deadlines or lateness.

## Cross-cutting rules

| Rule                                     | Behaviour the frontend relies on                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session                                  | `401` with `code: session_expired` or `unauthenticated`. Expired sessions keep unsaved input on screen; other pages route to sign-in.                                                                                                                                                                                                                                                                |
| Scope (PRD §5.2, AT01–AT02)              | Institution users see only their institution; officers only **currently** assigned institutions; supervisors only institutions **currently** supervised by them (see Supervision); administrators see all. Out-of-scope reads return **404** (no names, counts or files leak). Forbidden actions return **403**.                                                                                     |
| No scores before publication (O06, AT18) | Institution-facing responses (`report`, `receipts`, `foundations`, `results`) never contain points or fractions before release. Receipts say only `calculation: recorded` or `pending_baseline_approval`.                                                                                                                                                                                            |
| Pending, never zero (§10.5)              | Scores are `{ status: 'pending', reason }` or `{ status: 'calculated', fraction, points }`. Points are strings, half-up to two decimals, computed from exact fractions.                                                                                                                                                                                                                              |
| Optimistic concurrency                   | Drafts carry `version`; saves send `baseVersion` and get `409 version_conflict` when stale. Review writes carry the `revision` they assessed; `409 version_conflict` if not the latest (AT10).                                                                                                                                                                                                       |
| Idempotency (AT06)                       | `POST …/submit` requires `Idempotency-Key`; a repeat returns the original receipt with no second revision.                                                                                                                                                                                                                                                                                           |
| Audit and notifications (FR10–FR11)      | Every write listed below records an audit event and, where noted, notifies recipients once per event, recipient and channel. Email content is a minimal summary with a link. `link` is a portal path suited to the recipient's role (the institution's report, the officer's institution page); clock-driven notices carry the business time of their boundary, not the time the clock was advanced. |

### Authentication (PRD §13.1)

| Method and path                           | Roles | Notes                                                                                                                                                                                                          |
| ----------------------------------------- | ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/auth/config`                    | –     | `{ passwordSignIn, demoAccounts, demoPassword, providers: [{ id, name, status: available\|planned, description }] }`. Drives the sign-in page. Production returns `demoAccounts: false`, `demoPassword: null`. |
| `GET /api/demo/accounts`                  | –     | Demo mode only; active (set-up) accounts. Must not ship.                                                                                                                                                       |
| `POST /api/auth/password-reset`           | –     | `{ email }` → always `202` with the same message, whether or not the email has an account, so the form cannot find accounts. Sends a reset link to active accounts.                                            |
| `GET /api/auth/tokens/:token`             | –     | Describes an invitation or reset link: `{ purpose: invitation\|reset, email, displayName, expiresAt }`. `404 link_invalid` (unknown, used or replaced), `410 link_expired`.                                    |
| `POST /api/auth/tokens/:token`            | –     | `{ password }`. Sets the password, spends the link and signs the person in (returns `Session`). `422 weak_password` with `fieldErrors.password`.                                                               |
| `POST /api/account/password`              | any   | `{ currentPassword, newPassword }` → `204`. `422 invalid_password` (`fieldErrors.currentPassword`) or `422 weak_password` (`fieldErrors.newPassword`). Cancels any outstanding reset link.                     |
| `POST /api/settings/users/:id/invitation` | A     | Emails a fresh invitation to an invited account; the earlier link stops working. `409 not_invited` once the account is set up or deactivated.                                                                  |

- **Accounts are invited, never given a password.** Creating a user (directly, with a new institution, or by CSV import) creates the account in status `invited` and emails a single-use link to `/set-password?token=…`. The person chooses their own password there. Invitation links last 7 days; reset links 1 hour. `ManagedUser.status` is `active`, `invited` or `deactivated`, with `invitationExpiresAt` for invited accounts.
- **Errors never reveal accounts.** Every sign-in failure (unknown email, wrong password, invited or deactivated account) is `401 invalid_credentials` with one message. After 5 failures for an email within 15 minutes, sign-in for that email returns `429 too_many_attempts` for 15 minutes.
- **Password rules** (NIST SP 800-63B), shared as `passwordProblems()` in the contracts: 12 to 128 characters, not a common password, not containing the email's local part. No composition rules, no forced expiry; paste and password managers work (PRD §11).
- **What the real API must do beyond the mock:** hash passwords with Argon2id (or bcrypt); store only a hash of each token; issue the session as an HTTP-only, `Secure`, `SameSite=Lax` cookie and rotate it on sign-in; throttle per email and per IP on the server; audit sign-in, activation, reset and change (the mock records these); send email only through the delivery service, never an in-app notification carrying a link.
- **eCitizen (planned, not connected).** `providers` lists eCitizen with `status: planned`; the UI explains it and does not attempt a sign-in. If an agreement is reached, it would be OpenID Connect (authorization code with PKCE): eCitizen confirms identity; the platform links the eCitizen subject to the existing account with the same verified email on first use, and keeps roles, institutions and deactivation under the administrator. No national ID number is stored. Nothing in this demonstration implies such an agreement exists.

### Accounting Officers and focal persons (PRD §3.1, §7.2, §12.1)

The Accounting Officer is a contact on the institution (`Institution.accountingOfficer`: name, designation, optional email and phone), not a platform account: they chair the CPC, and their approval reaches the platform as the approval reference on each submission; P0 has no approver role. Focal persons are the institution's platform accounts (role `institution`); an institution can have several. The import columns are `institution_id, name, type, officer_email, ao_name, ao_designation` (required) and `ao_email, ao_phone, focal_name, focal_email`.

### Supervision (PRD §5.1, §5.2, §7.3)

Supervisors oversee the officers who review their institutions. Each institution has at most one current supervisor, assigned by the administrator with a reason and kept in history, exactly as officer assignments are. A supervisor reads only the institutions currently assigned to them, everywhere: directory, obligations, reviews, evidence, oversight metrics and workload, annual readiness and the consolidated report and export. An institution without a supervisor is visible to no supervisor, and the administrator's screens say so.

- **Institution setup:** `POST /api/settings/institutions` takes `supervisorId` (nullable). A live system would send it daily; replayed boundaries never repeat it.

### Day counting (PRD §9.1, FR02)

`Cycle.dayCounting` is the single rule for the cycle. It also holds `reviewTargetDays`, the officer review target: counted days from the current revision's receipt to a final decision. Past it, the quarter carries the `review_overdue` flag for officers, supervisors and administrators; institutions never receive it. It is a target, never a gate. Calendar mode counts every day (the PRD default); working mode counts Monday to Friday in Africa/Nairobi, skipping `holidays`. The rule drives: the deadline rule (`reportingDays` after quarter end, applied only to quarters that have not opened), clarification windows (`clarificationDays`; each clarification stores `windowDays` and `windowUnit` as issued and is never shortened by a later change), reminder times (N counted days before the deadline) and days late (`daysLate` with `daysLateUnit` on obligations, receipts and annual quarters; receipts keep the unit in force when issued). Lateness itself is always the instant comparison with the stored deadline.

### Administrator override (FR10)

Review actions belong to the assigned officer. An administrator may take one only with an `X-Override-Reason` header of at least 20 characters; each use writes a `review.override` audit event with the action and justification. `ReviewBundle.canOverride` tells the UI when an override is possible.

## Export column dictionary (`cpi-export-1`, FR16)

`GET /api/annual/report.csv` and `GET /api/results/export.csv` return one row per foundation component and per quarter of each published result:

| Column                    | Meaning                                                                         |
| ------------------------- | ------------------------------------------------------------------------------- |
| `schema_version`          | Always `cpi-export-1`.                                                          |
| `simulation`              | `true`: the demonstration profile, not official EACC scoring.                   |
| `cycle_id`                | Stable cycle identifier, e.g. `FY2026-27`.                                      |
| `scoring_profile_version` | The profile the result was scored with.                                         |
| `institution_id`          | Stable institution identifier, e.g. `DEMO-001`.                                 |
| `period_id`               | Quarter identifier; empty for foundation rows.                                  |
| `submission_revision`     | The finalized revision behind a quarter row; empty for foundations.             |
| `indicator_id`            | `procedures`, `risk_assessment`, `mitigation_plan` or `implementation`.         |
| `maximum_points`          | Points available for the row under the profile.                                 |
| `earned_points`           | Points earned, two decimals, half-up from exact fractions; empty while pending. |
| `status`                  | Disposition or score status, with `(late)` for a late quarter.                  |
| `published_at`            | Release time, ISO 8601 with offset.                                             |
| `publication_version`     | 1 for the first release; higher after a correction.                             |

Cells that begin with `=`, `+`, `-`, `@`, a tab or a carriage return are prefixed with `'` so spreadsheets do not run them as formulas. A minimal JSON report (`GET /api/annual/report`):

```json
{
  "schemaVersion": "cpi-export-1",
  "simulation": true,
  "generatedAt": "2027-08-01T08:00:00+03:00",
  "cycleLabel": "FY 2026/27",
  "profileName": "Hackathon Mock v1",
  "released": [
    {
      "institutionId": "DEMO-001",
      "version": 1,
      "evaluation": { "total": { "status": "calculated", "points": "88.75" } }
    }
  ],
  "unreleased": [
    {
      "institutionId": "DEMO-005",
      "reasons": ["Q3 not submitted and not yet closed"]
    }
  ]
}
```

Development-only mock routes under `/api/__mock/*` (reset, session expiry, latency, email failure, fault injection) are not part of the contract.
