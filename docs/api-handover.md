# API handover: contracts the frontend depends on

Status: current contract (HP2-9) · Implemented by the persisted API in `apps/api` (default) · Mirrored by the mock in `apps/web/src/mocks/` for unit tests and offline development

This document lists every endpoint the web app calls, who may call it, and the rules the screens rely on. The persisted API (`apps/api`: PostgreSQL, Redis and S3-compatible storage) implements them and is what the web app, `pnpm test:e2e` and CI use; its integration tests (`apps/api/src/**/*.int.test.ts`) check each rule, and [prd-coverage.md](prd-coverage.md) maps requirements to them. The mock implements the same contract for Vitest and `VITE_API_MODE=mock`. Where the PRD leaves a choice open, the API takes the PRD's proposed default; change it here, in the schemas and in both implementations together.

This page is the endpoint contract only. Architecture and services: [HP2-40](https://linear.app/hp2js/issue/HP2-40) and [platform-contracts.md](platform-contracts.md) (HP2-10: sessions, Redis, notification delivery, secrets, outages); files: [storage.md](storage.md) (HP2-19); entities and state transitions: [data-model.md](data-model.md); clock and resets: [simulation.md](simulation.md); latest results: [verification-results.md](verification-results.md).

## How to use this

- **Entities and state transitions** are explained in [`data-model.md`](data-model.md).
- **Schemas** live in `packages/contracts/src/draft/` (zod, exported from `@cpi/contracts`). The frontend validates every response against them, so a shape mismatch shows as "The server returned an invalid response". Adopt them in Nest with the existing `SchemaValidationPipe`, or revise them and update the frontend in the same change.
- **Errors** use the existing envelope `{ message, fieldErrors?, requestId?, code? }`. The frontend branches on `status` and `code` (listed below), shows `message` to users, and maps `fieldErrors` keys to fields. Messages must never contain submitted content.
- **The mock and the real API:** the web app uses the real API by default and `pnpm test:e2e` runs against it. The mock remains a second implementation for Vitest and `VITE_API_MODE=mock` development, so a behaviour change is made in both, with pure rules shared through `@cpi/contracts` (`src/domain/`), an integration test in `apps/api` (`pnpm test:integration`) and a unit test in `apps/web/src/mocks`.
- **Times** are ISO-8601 instants with an offset. Business time comes from the server's clock (simulated in the demo); the browser never decides deadlines or lateness.

## Cross-cutting rules

| Rule                                     | Behaviour the frontend relies on                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session                                  | `401` with `code: session_expired` or `unauthenticated`. Expired sessions keep unsaved input on screen; other pages route to sign-in.                                                                                                                                                                                                                                                                |
| Scope (PRD §5.2, AT01–AT02)              | Institution users see only their institution; officers only **currently** assigned institutions; supervisors only institutions **currently** supervised by them (see Supervision); administrators see all. Out-of-scope reads return **404** (no names, counts or files leak). Forbidden actions return **403**.                                                                                     |
| No scores before publication (O06, AT18) | Institution-facing responses (`report`, `receipts`, `foundations`, `results`) never contain points or fractions before release. Receipts say only `calculation: recorded` or `pending_baseline_approval`.                                                                                                                                                                                            |
| Pending, never zero (§10.5)              | Scores are `{ status: 'pending', reason }` or `{ status: 'calculated', fraction, points }`. Points are strings, half-up to two decimals, computed from exact fractions.                                                                                                                                                                                                                              |
| Optimistic concurrency                   | Drafts carry `version`; saves send `baseVersion` and get `409 version_conflict` when stale. Review writes carry the `revision` they assessed; `409 version_conflict` if not the latest (AT10).                                                                                                                                                                                                       |
| Idempotency (AT06)                       | `POST …/submit` requires `Idempotency-Key`; a repeat returns the original receipt with no second revision.                                                                                                                                                                                                                                                                                           |
| Audit and notifications (FR10–FR11)      | Every write listed below records an audit event and, where noted, notifies recipients once per event, recipient and channel. Email content is a minimal summary with a link. `link` is a portal path suited to the recipient's role (the institution's report, the officer's institution page); clock-driven notices carry the business time of their boundary, not the time the clock was advanced. |

### Authentication (PRD §13.1)

| Method and path                           | Roles | Notes                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------- | ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/auth/config`                    | –     | `{ passwordSignIn, demoAccounts, demoPassword, providers: [{ id, name, status: available\|planned, description }] }`. Drives the sign-in page. Production returns `demoAccounts: false`, `demoPassword: null`.                                                                                          |
| `GET /api/demo/accounts`                  | –     | Demo mode only; active (set-up) accounts. Must not ship.                                                                                                                                                                                                                                                |
| `POST /api/auth/password-reset`           | –     | `{ email }` → always `202` with the same message, whether or not the email has an account, so the form cannot find accounts. Sends a reset link to active accounts.                                                                                                                                     |
| `GET /api/auth/tokens/:token`             | –     | Describes an invitation or reset link: `{ purpose: invitation\|reset, email, displayName, expiresAt }`. `404 link_invalid` (unknown, used or replaced), `410 link_expired`.                                                                                                                             |
| `POST /api/auth/tokens/:token`            | –     | `{ password }`. Sets the password, spends the link and signs the person in (returns `Session`). `422 weak_password` with `fieldErrors.password`.                                                                                                                                                        |
| `POST /api/session/code`                  | –     | `{ challengeId, code }` → `Session`. `401 invalid_code` (counts towards the sign-in lockout), `410 code_expired` (10 minutes, used, or five wrong codes), `422 invalid_request`.                                                                                                                        |
| `POST /api/account/password`              | any   | `{ currentPassword, newPassword }` → `204`; `currentPassword` is not needed while replacing the temporary password, and the new one must differ from it. `422 invalid_password` (`fieldErrors.currentPassword`) or `422 weak_password` (`fieldErrors.newPassword`). Cancels any outstanding reset link. |
| `POST /api/settings/users/:id/invitation` | A     | Emails a fresh temporary password to an invited account; the earlier one stops working. `409 not_invited` once the account is set up or deactivated.                                                                                                                                                    |

- **Accounts are invited with a temporary password.** Creating a user (directly, with a new institution, or by CSV import) gives the account a random temporary password (only its scrypt hash is stored) and emails it once the change commits. It works for 7 days. After signing in with it (and the emailed code), every endpoint except `GET /api/session`, `GET /api/account` and `POST /api/account/password` answers `403 password_change_required` until the person chooses their own password; the web app routes them to `/choose-password`. `ManagedUser.status` is `invited` until then (`invitationExpiresAt` is the temporary password's expiry), then `active`; or `deactivated`. Reset links last 1 hour. Accounts invited by link before this change can still use their link.
- **Seeding and the configured administrator.** An empty database (and `pnpm db:seed`) is seeded according to `DEMO_MODE`: the fictional year in demo mode; otherwise a clean cycle (periods, form, scoring profiles, institution types, clock) with no institutions or people. In both modes `ADMIN_EMAIL`/`ADMIN_NAME` add an administrator (fixed ID `platform-admin`) who is emailed a temporary password when first created; resets and new simulation runs keep the account and its password and send nothing. `ADMIN_EMAIL` is required when `DEMO_MODE=false`, since no seeded account can sign in then. Without demo mode, a new simulation run and the scripted year answer `409 demo_only`, because they would replace real records. In demo mode they also need the dedicated demo database (name ending in `_demo`), else `409 not_demo_database`; `pnpm db:seed` refuses likewise (HP2-42). To invite another administrator from the command line: `pnpm user:invite-admin person@agency.go.ke "Full Name"` (in Docker: `docker compose exec api pnpm user:invite-admin …`). Focal persons added with an institution follow the same address rule as users; Accounting Officer contact emails stay fictional.
- **Two-step sign-in.** A right email and password never starts a session by itself: it emails a 6-digit code (Redis, hashed, 10 minutes, 5 tries). Demo one-click sign-in (demo mode only) skips it.
- **Account emails** (temporary passwords, sign-in codes, reset links) are React Email templates in `apps/api/src/email/`, sent through Resend when `RESEND_API_KEY` is set (from `EMAIL_FROM`), otherwise written to the email sink. They carry secrets, so they never enter the delivery outbox. A failed invitation email answers `503 email_failed` after the account is saved (use Resend invitation); a failed code email answers `503 email_failed`; a failed reset email is only logged, so the answer stays the same for every address. Workflow notifications still use the simulated outbox.
- **Errors never reveal accounts.** Every sign-in failure (unknown email, wrong password, invited or deactivated account) is `401 invalid_credentials` with one message. After 5 failures for an email within 15 minutes, sign-in for that email returns `429 too_many_attempts` for 15 minutes.
- **Password rules** (NIST SP 800-63B), shared as `passwordProblems()` in the contracts: 12 to 128 characters, not a common password, not containing the email's local part. No composition rules, no forced expiry; paste and password managers work (PRD §11).
- **How the API implements this** (scrypt hashes, hashed tokens and codes, the `HttpOnly` session cookie, per-email throttling, revocation and Redis outages): see [`platform-contracts.md`](platform-contracts.md#authentication-and-sessions).
- **eCitizen (planned, not connected).** `providers` lists eCitizen with `status: planned`; the UI explains it and does not attempt a sign-in. If an agreement is reached, it would be OpenID Connect (authorization code with PKCE): eCitizen confirms identity; the platform links the eCitizen subject to the existing account with the same verified email on first use, and keeps roles, institutions and deactivation under the administrator. No national ID number is stored. Nothing in this demonstration implies such an agreement exists.

### Forms (FR03)

| Method and path                 | Roles                    | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/forms`, `/:id`        | A; others published only | Drafts are administrator-only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `PUT /api/forms/:id`            | A                        | Draft only (`409 version_locked` otherwise). Send `baseRevision` from the version read; a stale one is `409 version_conflict`, so two administrators cannot overwrite each other. Each save increments `revision`, recomputes `changes` and is audited (`form.draft_save`). Weights come from the scoring profile. Labels, titles and options may be blank in a draft; publication refuses them.                                                                                                                                                                                                                                                              |
| `GET /api/forms/:id/validation` | A                        | `{ valid, issues: [{ path, message }] }`; paths like `sections.1.questions.2.label`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `POST /api/forms/:id/publish`   | A                        | `422 publication_blocked` with `fieldErrors` keyed by path (AT03). Rules: weights total 100; unique IDs; exactly one scored `milestone_progress` block; every period covered; started periods keep their version; scored criteria unchanged after activation. Locks weights for the cycle. Also: a question ID used by any earlier version cannot return as another type (nor a column ID); checklists need items; repeated rows need labelled columns, choice columns two options, and fewest ≤ most rows; limits must fit the type and be ordered. Publishing notifies institutions, officers and supervisors with the quarters and a summary of `changes`. |
| `POST /api/forms`               | A                        | New draft from the latest version; `409 draft_exists`. Audited (`form.draft_create`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `DELETE /api/forms/:id`         | A                        | `{ reason }` ≥ 10 characters. Discards an unpublished draft (audited `form.discard`); a published version (`409 version_locked`) and the first version (`409 first_version`) cannot be discarded.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

Form versions carry `revision` and `changes: [{ kind: added | removed | changed | periods, target: question | section | form, id, label, details[] }]`, the differences from `basedOnVersion`. Question types add `checklist` (`items: [{ id, label }]`, answered `{ items: { [itemId]: true | false | null } }`; required means every item is marked done or not done) and `repeated` (`columns: [{ id, label, type: text | number | date | yes_no | choice, required, choices?, limits? }]`, `minRows`, `maxRows`, answered `{ rows: [{ [columnId]: value }] }`). Any number, text or date question, and number columns, may carry `limits: { min, max, integer, unit, maxLength, earliest, latest }`. The completeness check reports a broken limit as missing, with a message such as "Enter a number from 0 to 500 staff."; `describeLimits` and `limitProblem` in `@cpi/contracts` give the same wording to the report form.

### Accounting Officers and focal persons (PRD §3.1, §7.2, §12.1)

The Accounting Officer is a contact on the institution (`Institution.accountingOfficer`: name, designation, optional email and phone), not a platform account: they chair the CPC, and their approval reaches the platform as the approval reference on each submission; P0 has no approver role. Focal persons are the institution's platform accounts (role `institution`); an institution can have several. The import columns are `institution_id, name, type, ao_name, ao_designation` (required) and `officer_email, ao_email, ao_phone, focal_name, focal_email` (a blank `officer_email` means no reviewing officer yet; one that is given must match an active officer).

### Supervision (PRD §5.1, §5.2, §7.3)

An institution without a supervisor is visible to no supervisor, and the administrator's screens say so.

### Prevention officers (PRD §5.1, §5.2, §10.4)

Officers review only the institutions currently assigned to them. Beyond the review endpoints they read: the rules in use (`GET /api/settings/profiles` and published forms, read only), their own portfolio through `GET /api/oversight` (scoped to their institutions; the workload row is theirs alone), the assignment history and current supervisor of their institutions, and their own reassignment requests.

- **Review digest:** as the clock crosses each boundary, each officer with something in their portfolio gets one `review.digest` notification: baselines still to approve for quarters starting within 14 days (a quarter's baseline must be approved before it opens), seeded baselines to confirm, reviews past or within 2 days of the review target, clarification windows that ended without a response, and quarters needing a final disposition after the cutoff.
- **Temporary cover and handover:** see `POST /api/assignments`. The covering officer sees who they cover for and until when; the handover note appears on the institution's page.
- **Conflict of interest:** an officer declares one with `POST /api/assignment-suggestions` (`kind: conflict_of_interest`). They keep access until the administrator reassigns.

### Day counting (PRD §9.1, FR02)

`Cycle.dayCounting` is the single rule for the cycle. It also holds `reviewTargetDays`, the officer review target: counted days from the current revision's receipt to a final decision. Past it, the quarter carries the `review_overdue` flag for officers, supervisors and administrators; institutions never receive it. It is a target, never a gate. Calendar mode counts every day (the PRD default); working mode counts Monday to Friday in Africa/Nairobi, skipping `holidays`. The rule drives: the deadline rule (`reportingDays` after quarter end, applied only to quarters that have not opened), clarification windows (`clarificationDays`; each clarification stores `windowDays` and `windowUnit` as issued and is never shortened by a later change), reminder times (N counted days before the deadline) and days late (`daysLate` with `daysLateUnit` on obligations, receipts and annual quarters; receipts keep the unit in force when issued). Lateness itself is always the instant comparison with the stored deadline.

### Administrator override (FR10)

Review actions belong to the assigned officer. An administrator may take one only with an `X-Override-Reason` header of at least 20 characters; each use writes a `review.override` audit event with the action and justification. `ReviewBundle.canOverride` tells the UI when an override is possible.

## Export (`cpi-export-2`, PRD §12.3, FR13, FR16)

Four endpoints return the same rows. The CSV's columns are the JSON row keys, in this order:

- `GET /api/annual/report.csv` and `/api/annual/report.json` (supervisor, administrator): every institution in scope, released and unreleased.
- `GET /api/results/export.csv` and `/api/results/export.json` (institution): its own current released result only; 404 `not_published` before release.

Each released result has one `annual_total` row, one row per foundation and one per quarter. Every download is recorded in the audit log (`export.download`). The rows are built by `exportPayload` in `packages/contracts/src/domain/export.ts`, which the API and the mock share, so their exports are identical.

**Formats.** Timestamps are ISO 8601 in UTC (`Z`), in columns ending `_utc`. Points are annual points out of 100, as decimal strings with two places, rounded half up from exact fractions. Days late are whole days in `days_late_unit`. The JSON payload repeats these in `formats`.

**Compatibility.** `cpi-export-2` replaces `cpi-export-1` and is not backwards compatible. It adds the total, names and traceability columns, and moves lateness out of `status` into `late`. `scoring_profile_version` is now the profile version, not its name, and `simulation` comes from the profile.
